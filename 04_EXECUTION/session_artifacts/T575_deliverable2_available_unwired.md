# Deliverable 2 — Available-but-Unwired Inventory

**Scope:** T-575 (feature-space-audit), Fork B. Read-only inspection of `src/`, `scripts/`, `qualitative_data/`, and referenced logs/archives. No code, model, or constant was changed. All findings below are grouped by the operator's own axes. Each item states: the attribute, where it already exists, and what it would take to reach a model.

**Verification note:** everything below is drawn from static code/data inspection in an isolated worktree, per the task's read-only constraint (no live API calls, no VPS access, no re-running T4). Where a finding depends on runtime behavior (e.g., whether a field is actually ever populated), that is stated explicitly as *inferred, not live-verified*.

## Situational

- **Live score margin / game state (blowout vs. close game).** Fetched at C1: `mlb_ingestion.py` (`fetch_completed_games`, hydrate `linescore,team`) populates `home_runs`/`away_runs` (lines ~753-754) for completed-game ingestion. **Not present at all** in `MLBLiveBatterState` (`run_t4_mlb_live.py:281-288` — fields are only `player_id, player_name, h_so_far, ab_so_far, inning, game_id`), so T4's live per-cycle evaluation never sees score differential, and `t4_mlb_cycle_log.jsonl` records no score field. **To reach a model:** add a live scoreboard fetch (ESPN linescore, same pattern as the completed-game path) into the T4 poll loop, extend `MLBLiveBatterState` with a score/margin field, and pipe it into `p_t4`'s inputs or into a leverage-conditional signal. Notably, `qualitative_amplifier.py`'s own design doc (CTX-1, "game closeness proxy") already names exactly this kind of signal as a target amplification context for the *NBA* qualitative layer — the concept exists in the codebase's own design language but has never been implemented for MLB or for T4.
- **Batting slot.** Exists and **is wired** — sourced from a T2 same-day file (`_load_t2_batting_slots()`, `run_t4_mlb_live.py:455`) and consumed directly in `_compute_ab_remaining()` (line 384) via the `_AB_BY_SLOT` table, which feeds `p_t4`. Included for completeness since it's adjacent to the unwired items above, not a finding.
- **Innings-remaining / late-game leverage.** `inning` is captured in `MLBLiveBatterState` and used only to bound `ab_remaining` (line 384), not as an independent leverage signal (e.g., no separate "close-and-late" flag). **To reach a model:** would need a derived feature (inning ≥ 7 AND |score margin| ≤ 2) combining the score field above (not yet wired) with the existing `inning` field.

## Sport (cross-sport comparison)

- **NFL passing_epa / rushing_epa split.** Both are real, fetched raw columns — `_NFL_TEAM_STATS_COLUMNS` (`nfl_ingestion.py:133-145`) includes `passing_epa, rushing_epa` explicitly, and `off_epa` is *derived from them* at ingestion time (`off_epa = passing_epa + rushing_epa`, line 244). They reach the C1 team-stats table intact. But `nfl_exp027_adapter.py` (the only live NFL model) calls only `store.get_off_epa()` / `get_def_epa_allowed()` (lines 180-195) — the aggregate, never the split. **To reach a model:** add `get_passing_epa()`/`get_rushing_epa()` accessors to `NFLTeamStatsStore` (they likely already exist on the underlying rolling-window machinery since `off_epa` is summed from them) and add two features + retrain via `exp027_hyp012_nfl_moneyline_backtest.py`. Since EXP-027's own verdict is UNDERPOWERED, this is a candidate follow-on hypothesis, not a bug — flagging as available, not recommending pursuit here (out of this task's scope).
- **MLB pitcher full game-log detail.** `MLBPitcherStatsStore` computes `get_era_l5`, `get_k_per_9_l5`, `get_bb_per_9_l5` — three rolling aggregates — from an underlying per-start log (`add_pitcher_log()`). Fields likely available in the raw log beyond these three aggregates (e.g., pitch count, WHIP, HR/9) were not directly confirmed in this pass (store internals not fully read) but the aggregation pattern (`_era()`, `_k_per_9()`, `_bb_per_9()` helper functions feeding rolling means) strongly suggests the raw per-start rows carry more than three summary stats. **To reach a model:** would require a full read of `mlb_pitcher_stats_store.py`'s log-ingestion schema to confirm what's discarded at aggregation.

## Player

- **`get_opp_runs_scored()` — computed, never consumed.** `MLBTeamStatsStore` (`mlb_team_stats_store.py`) implements both `get_opp_runs_allowed()` and `get_opp_runs_scored()`. Only `get_opp_runs_allowed()` is called anywhere in `mlb_features.py`'s `compute_features_bulk()` — confirmed via direct read of that pipeline. `get_opp_runs_scored()` has zero call sites in `mlb_features.py`. **To reach a model:** it's a one-line addition — call the existing method and add `opp_runs_scored_l10` to `_MLB_FEATURE_CSV_COLUMNS` in `data_contracts.py` plus the corresponding `MLBFeatureStore` row-build step. The store-side work is already done; only the C2 wiring and contract-column addition are missing.
- **PRF / Qualitative framework (PAM v4) — real, populated, never reaches MLB.** `qualitative_store.py`'s `QualitativeSignalStore` is a genuine, non-stub implementation (contra its own class docstring, which incorrectly claims "Status: SKELETON" — see Documentation Accuracy note below) that loads real classification data from `qualitative_data/pam_v4/QS-2026-05-28-001_classifications.csv` and `...-002_classifications.csv`, producing 15 one-hot archetype weights (`prf_w01`-`prf_w15`) + 32 modifier flags (`mod_01`-`mod_32`) = 47 features (F-103-F-181), joined by `player_id` + `game_date` under temporal validity. Consumer grep (`grep -rln "QualitativeSignalStore\|qualitative_amplifier\|QualitativeAmplifier" src/ scripts/`) hits only NBA-generic files (`run_exp006.py`...`run_exp016.py`, `train_model_v2*.py`, `run_t177_v2_backtest.py`, `run_paper_trade.py`, `run_pregame.py`, `run_t4_inplay.py`). Direct greps against `run_mlb_pregame.py`, `run_t4_mlb_live.py`, `run_mlb_paper_trade.py` for `qualitative|Qualitative|PRF|prf_` all return **0 hits**. **Finding: the entire PRF layer — real code, real data — is wired only into the NBA pipeline, which is DARK/FROZEN per standing operator directive. It contributes nothing to the live MLB books (T1 or T4).** **To reach a model (MLB):** would require (a) an MLB-specific PAM classification pass over MLB players (the existing CSVs are NBA archetypes — heliocentric/rim-protector/etc. do not transfer), (b) wiring `QualitativeSignalStore.enrich_features()` into `mlb_features.py`'s pipeline, and (c) an MLB-relevant amplification-context redesign in `qualitative_amplifier.py` (its CTX-1..CTX-5 contexts are basketball-specific: plus_minus trend, pts_cold_flag, min_season_mean). This is a substantial, multi-part build, not a wiring fix.
- **`doubles`, `triples`, `hr`, `rbi` (individually).** Fetched at C1 (present in `_MLB_BATTER_COLUMNS`) but only reach C2/model as components of composite rates (`slg_l10`, `ops_l10`) — no standalone `hr_l10`, `doubles_rate_l10`, etc. beyond what's already listed (`hr_rate_l10` does exist per the contract). **To reach a model:** straightforward — the raw counts are already in the rolling window; would need new column definitions in `_compute_rolling_batter_features()` plus contract entries.

## Team

- **Opponent bullpen quality.** Only the probable/known starting pitcher is scored (`opp_sp_era_l5`, `opp_sp_k9_l5`, `opp_sp_bb9_l5`, `opp_sp_is_known`). No bullpen aggregate exists anywhere in the C1/C2 layers inspected (`MLBPitcherStatsStore` methods are all keyed to a single pitcher). **To reach a model:** would require a new C1 fetch (team bullpen ERA/game logs) and a new store — this is a build, not a wiring gap, since no bullpen data is fetched at all today.
- **`park_factor_hits` — very likely dead/inert in production (inferred, not live-verified).** `mlb_features.py`'s `_park_factor()` looks up a static 30-venue dict (`_PARK_FACTOR_HITS`) keyed by **venue name**, sourced from `game_starters[game_id]["venue_name"]`. But `fetch_game_starters()` in `mlb_ingestion.py` requests `hydrate: "probablePitcher,team"` — **`"venue"` is not in the hydrate string.** An inline comment at that call site (lines 558-560) claims *"venue hydrate returns 406 from DigitalOcean/Fastly CDN... park_factor_hits uses team abbr from static lookup so venue data is not needed at inference time."* This comment is internally inconsistent with the actual implementation on two counts: (a) there is no team-abbreviation-keyed park table anywhere in the codebase — the only park table is venue-name-keyed; (b) since `"venue"` is never requested, `game.get("venue")` returns `{}` and `venue_name` is `None` for essentially every game, so the lookup almost certainly falls through to the neutral default (1.000) on every row. **This is a documentation-vs-implementation contradiction, not something this task is authorized to fix** (read-only, no model/feature changes) — flagging for the parent synthesis. **To reach a model (i.e., to make it non-dead):** would need either (a) an alternate venue-identification path that survives the CDN 406 (e.g., a static `game_id`→venue or `home_team`→venue mapping, since home team already determines venue for the ~90% of games that aren't at a neutral site), or (b) switching the park table itself to be team-abbreviation-keyed to match what the comment claims already happens.

## Game

- **Doubleheader / game-number-of-day flag.** Not found anywhere in the C1/C2 inspection — `b2b_flag` (back-to-back days) exists, but no distinct flag for a same-day doubleheader (which materially changes rest/fatigue dynamics differently than a simple back-to-back). **To reach a model:** would need a new derived field from game scheduling data (multiple `game_id`s sharing a team + date).
- **Home/road trip length / travel.** Not present. `is_home_game` is binary per-game; no rolling "games into this trip" or timezone-change signal exists in any C1/C2 file inspected. **To reach a model:** would be a new feature requiring a schedule-sequence scan, not currently available even as raw data in the inspected ingestion layer.
- **Weather (wind/temp) at outdoor parks.** Not fetched anywhere in `mlb_ingestion.py`. Genuinely absent, not merely unwired — would require a new C1 data source (out of this task's scope per the operator directive: "do not build/wire any new data source").

## Scheme (cross-market-type / cross-band)

- **Cross-ticker, same-game correlation.** Confirmed via `risk.py` (`grep -n "correlat"` → zero hits) and `run_t4_mlb_live.py` (`_find_open_position_opposite_direction()` line 850 = intra-book same-ticker wash-trade block only; `_t1_open_position_opposite_direction()` line 876 = cross-book alarm-only, also same-ticker). **No mechanism anywhere models correlation between different tickers on the same underlying game** (e.g., a moneyline position and a total position on the same game, or two players' hit props in the same game). The only aggregate protection is `MAX_PORTFOLIO_DEPLOYMENT_PCT = 0.60` (`risk.py`), a blunt equity-wide cap, correlation-blind. `ADR-0053` §2.5 explicitly *names* a "game-key correlation group" mechanism (group open exposure by `(game_id, date)` across ticker families) but states it is **out of accepted implementation scope, requiring its own future ADR** — it exists only as a named-but-unauthorized proposal, not code. *(This directly answers Deliverable 4's scoping question; surfacing here for the parent's benefit since it fell out of this walk, not because it's this deliverable's assignment — Deliverable 4 owns the write-up.)*
- **T1↔T4 shared feature reuse.** T1 and T4 MLB are architecturally separate processes (ADR-0023 pool isolation) with no shared feature computation path — T4's `p_t4` uses only `ba_l10`/`ba_l10_shrunk` (empirical-Bayes shrunk average) plus live in-game counts; it does not consume T1's fuller feature set (`opp_sp_era_l5`, `park_factor_hits`, `opp_runs_allowed_l10`, etc.) at all. **To reach a model:** T4 could in principle join against the same daily feature CSV T1 produces for pregame context (SP quality, park factor once fixed) to condition its live update, rather than relying solely on rolling batting average. This is a design question (how T4's Bayesian update should incorporate pregame priors beyond `ba_l10_shrunk`), not merely a wiring fix.

## Summary of highest-signal findings (for parent synthesis)

1. **`park_factor_hits` is very likely dead (defaults to neutral 1.000 on every row)** — the venue-name it needs is never fetched, and the code comment excusing this misdescribes the actual lookup mechanism. Inferred from code structure only, not live-verified.
2. **The PRF/qualitative framework (real, implemented, populated with data) is completely absent from the live MLB pipeline** — it only reaches NBA, which is dark/frozen. Zero PRF signal exists in either live MLB book today.
3. **`get_opp_runs_scored()` is computed by the team-stats store and never consumed** — the cheapest available-but-unwired item in this inventory (data already exists, one line of C2 wiring away).
4. **NFL's `passing_epa`/`rushing_epa` split is fetched and stored but the only live model (EXP-027) consumes just the summed `off_epa`** — a real disaggregation opportunity, not built.
5. **No score-state / game-leverage signal reaches T4's live evaluation at all** (`MLBLiveBatterState` has no score field) — notable because the qualitative-amplifier design docs (NBA-side) already articulate exactly this kind of context-conditional amplification concept, just never implemented for MLB/T4.
6. Cross-ticker same-game correlation is unmodeled by design choice (ADR-0053 §2.5 names it, defers it) — surfaced for Deliverable 4, not owned here.
