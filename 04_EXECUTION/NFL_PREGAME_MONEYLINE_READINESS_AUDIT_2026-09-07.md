## Answer, up front

**No. One NFL pregame moneyline bet cannot be placed by 2026-09-09.**

**Binding constraint: Step 6 (Resolution).** There is no moneyline/game-winner settlement logic anywhere in `src/`, for any sport — not merely absent for NFL. `paper_trader.py::settle_position()`, the only generic settlement function that exists, is structurally a numeric threshold-crossing check (`actual_stat >= threshold`) and cannot express a categorical game-winner outcome at all. This is not a missing data source; it is a missing code path, and one that (per the Kalshi ticker format observed in Step 1) would need to be built before Step 1's own parser fix is worth making. Independently, Step 1 (Market fetch) is also a hard blocker: the bot's own Kalshi client returns zero parsed NFL moneyline or spread markets today, live-verified (see below), due to a schema mismatch, not a bug in one line.

**Even if Steps 1–6 were all built today, GG-203 blocks submission regardless** — every Kalshi order write has failed for every sport, 100% of the time, for 24 consecutive days as of this audit (since 2026-08-15T00:06:20Z, still unresolved as of the most recent DECISION_LOG evidence, T-515/2026-09-03). GG-203 is an external, Kalshi-account-wide, ticker-independent order-write fault with no in-repo fix — it is a **fully independent, compounding blocker**, not one of the six steps and not something this audit's scope can move. Whether Kalshi resolves it tomorrow or in a month is outside this repo's control.

**Earliest realistic date: not before 2026-09-23**, and only if GG-203 resolves independently in that window. That estimate assumes: Step 6 (moneyline settlement logic, sport-agnostic, ~2-3 days), Step 1 (schema fix, ~1-2 days), Step 2 (NFL C1 ingestion module, ~2-3 days), Step 3 (confirm/adapt LR model class, ~0.5-1 day), Step 5 (wire measurement_stake + a run script + cron, ~1-2 days) are built and integration-tested sequentially by one person with no blocking surprises, which is optimistic. If GG-203 does not resolve independently in that window, the earliest date is **indeterminate** — a live bet cannot be placed while every order submission fails, no matter how complete the rest of the pipeline is.

## Six-step trace: NFL pregame moneyline bet, end to end

| # | Step | What exists | What is missing | Est. hours |
|---|------|-------------|------------------|-----------|
| 1 | **Market fetch** | Registry-driven `series_ticker_for()` (`market_type_registry.py:124`, `MarketType.NFL_MONEYLINE: "KXNFLGAME"`) correctly resolves the series ticker and the bot's `kalshi_client` **can** reach live NFL markets — confirmed live: raw unparsed `_get('/markets', ...)` calls return **64 open `KXNFLGAME` markets** and **200+ open `KXNFLSPREAD` markets** today. But the client's own `_parse_market()` (kalshi_client.py:427) returns **zero** parsed markets for both series when called through the bot's normal path. Root cause: `threshold = int(parts[-1])` inside a bare `except Exception: return None` — it expects the last ticker segment to be a numeric threshold (works by coincidence for `KXNFLTOTAL` tickers like `...-64`) and silently drops anything else, including moneyline tickers ending in a team code (`...-NYG`) and spread tickers ending in a signed number+team compound (`...-KC8`). The deeper issue: `PlayerMarket` (kalshi_client.py:~159), the dataclass `_parse_market()` returns, is player-prop-shaped by design (`player_name`, `team_abbr`, `threshold: int`) — there is no field, and no dataclass variant, that can represent "team A beats team B" or "team A covers N points." Fixing Step 1 is a schema addition (a new market dataclass or a generalized outcome representation), not a one-line parser patch. | **10-14** (schema design + new dataclass/branch + parser logic + tests against live tickers for all three NFL series) |
| 2 | **Model input** | A generic `team_stats_store.py` (`c1_signal_ingestion/team_stats_store.py`) exists, but it is NBA-shaped throughout: docstring frames it as "Phase 7 (Strategy B — opponent defensive rating feature, T-075)", built from `NBAIngestionClient.fetch_team_game_log()`, and its core computation (`pts_allowed = pts - plus_minus`) is an NBA-specific box-score derivation with no NFL analogue (`plus_minus` is not a standard NFL per-game stat). There is **no NFL-specific C1 ingestion module** — `c1_signal_ingestion/` has `mlb_ingestion.py`, `mlb_team_stats_store.py`, `mlb_pitcher_stats_store.py`, `ds02_nba_live.py`; nothing NFL. An LR moneyline forecast for NFL would need, at minimum: team offensive/defensive efficiency (rolling, recency-weighted), rest days, home/away, and ideally a strength-of-schedule adjustment. Public sources cover this (e.g. `nflverse`/`nflfastR`-derived play-by-play and schedule data, or ESPN's public NFL endpoints, which `ds02_nba_live.py`'s pattern already shows this codebase knows how to consume for a different sport) — the data exists publicly; the ingestion module to pull and shape it does not. | **16-24** (new C1 module + schema + integration with C2 feature derivation, modeled on the MLB precedent) |
| 3 | **Forecast** | HYP-011 pre-registers moneyline LR. The model class itself, per ADR-0004 (LR + Platt scaling), is stated in CLAUDE.md as applying "across sports until superseded by ADR" — i.e., sport-agnostic in *doctrine*. Reading the actual C3 path (`c3_forecasting/forecaster.py`) is necessary to confirm whether the code is genuinely sport-agnostic or has MLB-shaped assumptions baked in (feature-name coupling, hardcoded column lists, MLB-specific priors). This session read `forecaster.py` in full; the LR/Platt-scaling core is generic (operates on whatever feature vector it's given), but its default feature-name wiring and any MLB-specific calibration priors would need to be parameterized per sport rather than assumed — this is a moderate adaptation, not a rewrite. | **4-8** (parameterize feature set per sport, retrain/calibrate on NFL features once Step 2 exists — cannot fully complete until Step 2 lands) |
| 4 | **Risk gate** | `risk.py` (`c4_risk_engine/risk.py`) — hard limits (`_HARD_LIMITS`, `MAX_DAILY_LOSS_PCT`, `DEFAULT_KELLY_FRACTION`) are exposure-based and sport-agnostic by construction; `evaluate_forecast()` does not reference MLB or NFL by name anywhere in the gate logic itself. It does not currently evaluate an NFL cell today because no NFL forecast ever reaches it (Steps 1-3 are incomplete), but there is no NFL-specific blocker inside `risk.py` itself — this step is structurally ready, contingent on upstream steps. | **0-2** (verification/smoke-test only once an NFL forecast exists; possibly zero additional work) |
| 5 | **Execution** | `measurement_stake.py`'s `T1_GAME_MARKET_TYPES` frozenset (line 80-83) already includes all four NFL market types (`nfl_moneyline`, `nfl_spread`, `nfl_game_total`, `nfl_team_total`) — the ADR-0058 nine-cell T1 set is defined in code. But a precise import-statement grep (`^from.*measurement_stake import\|^import.*measurement_stake\|c5_execution\.measurement_stake`) confirms the module's **only real importer anywhere in `src/`/`scripts/` is `scripts/assert_ledger_invariants.py`**, an audit tool — nothing live calls it, for any of the nine cells, NFL's four or MLB's five. Per ADR-0059 (already known, re-confirmed): nothing is wired. There is also no NFL run script (no `run_t1_nfl.py` analogue to `run_t1_mlb.py`) and no NFL cron entry in `deploy/cron.conf`. | **8-12** (wire `measurement_stake` into a live pipeline path, write a run script modeled on the MLB T1 pattern, add cron entry, end-to-end smoke test) |
| 6 | **Resolution** | MLB uses the MLB Stats API for outcome settlement. **There is no NFL equivalent, and no moneyline-shaped settlement logic exists for any sport.** Read in full: `paper_trader.py::settle_position()` (line 915) implements `yes_won = actual_stat >= threshold` — a numeric threshold-crossing pattern built for stat-threshold markets (NBA points, MLB hits). This is structurally incompatible with a moneyline/game-winner categorical outcome ("did team X win," not "did a stat cross a number") — it isn't that NFL lacks a data feed plugged into this function, it's that the function's own outcome model cannot express what a moneyline bet resolves to, for any sport. A concrete NFL data source exists and is straightforward (ESPN's public NFL scoreboard/summary endpoints, or `nflverse` schedule+result data, either of which returns final score / winner directly) — the missing piece is entirely the settlement code path: a categorical-outcome resolver (generalized across moneyline, spread-with-line, and total-with-line) that plugs into the existing ledger/audit-log machinery the same way `settle_position()` does today. | **12-18** (design + build a generalized categorical settlement path, wire an NFL result source into it, test against real completed games — this also unblocks MLB's own currently-dormant moneyline/spread/total T1 cells, not just NFL) |

**Total, sequential, single-engineer, no surprises: ~50-78 hours (~1.5-2 calendar weeks of focused work), independent of GG-203.**
