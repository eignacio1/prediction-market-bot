BEGINNING THE PREDICTION MARKET BOT — STARTUP WORKFLOW (Context-Rot Resistant)
Version: 1.0
Purpose: Provide a step-by-step operating workflow to begin a prediction market bot project in a way that withstands context erosion, using the Project Directory Compass OS and PDTP rigor.
Portability: Tool-agnostic. Works whether you are building a trading agent, market-making bot, forecasting assistant, or research prototype.

NOTE ON GOVERNANCE
- If it isn’t in the directory (or linked from it), it doesn’t exist for governance/handoff purposes. (Compass OS principle)
- Major changes require a decision record (ADR). (Compass OS principle)

=====================================================================
1) DECONSTRUCTION (PASS 1)
=====================================================================
Decision restatement:
A decision will be made about how to start and operationalize the prediction market bot project (scope, architecture, execution plan, and governance) by the end of the initial setup window (typically 48–72 hours) using criteria: traceability, reproducibility, safety/compliance, and operational readiness.

Ambiguities to resolve early:
- Market venue: internal simulation vs external prediction market vs paper trading.
- Bot role: market maker vs directional trader vs forecaster vs arbitrage.
- Data sources: public news, internal research, structured feeds, human inputs.
- Execution constraints: latency, rate limits, capital limits, risk limits.
- Compliance constraints: permitted instruments/venues, recordkeeping, approvals.

Subproblems (P1–P6):
P1: Define scope, success criteria, and constraints (charter/spec).
P2: Define market mechanics + bot strategy class (research framing).
P3: Define architecture + interfaces (system design).
P4: Define reproducible execution environment + data provenance (run-ability).
P5: Define validation, monitoring, and risk controls (evidence + ops).
P6: Define governance workflow to prevent context erosion (Compass OS + PDTP).

Knowledge loading (disciplines activated):
- Market microstructure & prediction markets (mechanism design, liquidity, scoring rules)
- Quant research & forecasting (calibration, Brier/log loss, backtesting pitfalls)
- Software/infrastructure engineering (reliability, observability, change control)
- Risk management (limits, drawdowns, tail risk, kill switches)
- Security/compliance (access control, audit trails, data handling)
- Cognitive science / knowledge management (handoff design, retrieval cues)

P1) Scope, success criteria, constraints (Charter + Spec)
-------------------------

P2) Market mechanics + strategy class (Research framing)
-------------------------
Actions (Day 1–2):
1. Define the market mechanism:
   - Continuous double auction vs AMM vs order book vs bookmaker-like
   - Settlement rules, fees, tick sizes, position constraints
2. Choose strategy class (initially one):
   - Market making (spread + inventory control)
   - Directional trading (forecast -> position sizing)
   - Arbitrage (cross-market inconsistencies)
   - Forecast-only assistant (no execution)
3. Define evaluation metrics:
   - Forecast: Brier score, log loss, calibration curves
   - Trading: PnL, Sharpe, max drawdown, slippage, fill rates
4. Create EXPERIMENT_LOG template usage:
   - Hypothesis -> method -> data snapshot -> code ref -> results -> confidence

Outputs:
- 05_RESEARCH_EXPERIMENTS/RESEARCH_QUESTIONS.md
- 05_RESEARCH_EXPERIMENTS/HYPOTHESES.md
- 05_RESEARCH_EXPERIMENTS/EXPERIMENT_LOG/EXP-YYYY-MM-DD_*.md

3) SYNTHESIS & CONTRADICTIONS (PASS 3)
=====================================================================
Cross-domain synthesis:
- P2 (strategy class) constrains P3 (architecture) and P5 (validation). A market-making bot needs inventory/risk loops; a forecast-only bot needs evaluation/calibration but not execution safety.
- P4 (reproducibility) is the backbone for P5 (evidence). Without pinned environments and data snapshot IDs, validation evidence cannot be trusted.
- P6 (governance) prevents P1–P5 from drifting apart under parallel work by enforcing ADRs, interface contracts, and frozen baselines.

Contradiction scanning (common tension points):
- “Move fast” vs “audit-ready”: resolved by minimal enforcement set + artifact headers + ADR discipline.
- “Research flexibility” vs “production safety”: resolved by separating research artifacts (05) from execution controls (06/10) and using gates to promote changes.
- “Forecast accuracy” vs “PnL”: can diverge; must be explicit in charter metrics and validation plan.

4) ADVERSARIAL CRITIQUE & DEFENSE (PASS 3)
=====================================================================
Strongest attack:
“This workflow is too heavy for starting; you’ll spend days writing docs instead of building. Also, prediction markets are noisy; early validation may be misleading.”

Defense & reinforcement:
- Narrow the claim: In the first 72 hours, produce only the minimum viable canonical set (Charter, Requirements, Architecture sketch, Run Instructions, ADR-0001, TODO/RID, Memory Bank).
- Add guardrails: timebox documentation (e.g., 2 hours/day) and require that every doc has staleness triggers so it doesn’t rot.
- Stage validation: start with simulation/backtest sanity checks; defer high-confidence claims until evidence accumulates.
